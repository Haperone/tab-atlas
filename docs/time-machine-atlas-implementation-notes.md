# История коллекций Atlas: аудит перед реализацией

> Исторический аудит до интеграции. Писатели и UI уже переведены на новую модель;
> актуальное состояние и доказательства — в [atlas-history-progress.md](atlas-history-progress.md).

5 октября 2026. Проверен текущий код; это план необходимых изменений,
а не выполненная реализация. Контракт конфликтов папок согласован пользователем:
замена, merge недостающих ссылок либо копия с префиксом (§6 [ТЗ](time-machine-spec.md)).

## Источник данных

`extension/lib/storage-repository.js` определяет `folders`, `deferred` и
`workspaceSnapshots`. Для истории нужны только первые два ключа.

- Архив — `completed` записи, исключая `dismissed`:
  `extension/app.js:824` (`getSavedTabs`).
- `dismissed` — legacy tombstones. Они физически удаляются при запуске:
  `extension/app.js:899`, вызов `:5745`.
- Названия/цвет/locked/collapsed и порядок папок хранятся в `folders`;
  принадлежность ссылки — `folderId`, порядок ссылок — порядок `deferred`.
- Перенос/удаление папки может одновременно менять оба массива.
- Подтверждённая структура истории не должна содержать ссылок на исчезнувшую
  папку без явно определённого inbox назначения.

Исторический preview читает эти данные и не включает текущие browser tabs.
Workspace исключены, даже если импорт записывает все три ключа вместе.

## Писатели

| Путь | Текущее поведение | Требуемая интеграция |
| --- | --- | --- |
| Dashboard `app.js:788–1093` | Read/modify/set массивов через repository | Сохранение, completion/Undo, remove/Undo, папки, порядок, move должны использовать общий контракт изменений |
| Popup/ПКМ `quick-save-service.js:42`, `:98` | Прямой `area.set`, собственная worker queue | Та же очередь коллекций, включая create-folder + save и quick-save Undo |
| Backup `backup-data.js:405` | Read/merge/checkCapacity/setCollections | Проверка/merge по актуальной ревизии внутри общего владельца; workspace не входят в history |
| Shared import `share-import.js:66` | Decode, затем read/merge/set | Декодирование до мутации; проверка актуальных коллекций и commit в общем владельце |
| Startup/retention `app.js:1240`, `:5745` | Удаление legacy и expired archive | Явные логические операции, сериализация с restore/Undo и capture до/после |

`createStorageRepository` сейчас не предотвращает stale write. Очередь quick-save
сериализует только её собственные операции. Отдельная очередь restorer не может
защитить сохранение из dashboard. `storage.onChanged` сообщает результат после
записи; он не предоставляет compare-and-set или блокировку перед ней.

Пример потери: dashboard читает старый `deferred`; popup добавляет ссылку;
dashboard сохраняет своё старое содержимое после изменения папки. Новая ссылка
исчезает. Проверка ревизии с последующим несогласованным set в другом контексте
тоже оставляет окно гонки.

## Контракт записи

Предпочтительное направление: один worker-владелец принимает логические команды
из доверенных внутренних поверхностей, читает актуальные коллекции, применяет
существующие pure functions и сохраняет изменённые ключи одним `set`.

- UI передаёт намерение (`move ids`, `rename folder`, `remove ids`), а не массив,
  построенный по устаревшему чтению. Не повторять stale массив после конфликта.
- Для действий из preview/подтверждения использовать ожидаемую ревизию;
  при несовпадении план нужно обновить и показать последствия.
- Новая ревизия принадлежит commit, не историческому слепку. Restore не возвращает
  счётчик ревизии в прошлое и не переиспользует старую операционную идентичность.
- В очередь входят read/modify/checkCapacity/write и регистрация результата;
  browser UI/audio/инъекция receipt выполняются после commit вне критической секции.
- Единая операция удаления папки/импорта фиксируется согласованно, без capture
  состояния «папка уже удалена, ссылки ещё не перенесены».
- Обычное сохранение остаётся возможным при отказе history, с честным обозначением
  отсутствующего отрезка; restore запрещён без долговечного Before restore.
- Workspace-only операции не создают историю. При общем импорте учитывать их
  итоговый размер и не перезаписывать независимые актуальные данные старым массивом.
- Проверить sender и разрешённые действия для dashboard/popup; внешний сайт не
  получает права восстанавливать коллекции. Существующий ПКМ вызывает локальный
  сервис, а не доверяет командам страницы.

Не менять API repository одним универсальным «автоматическим merge»: удаление,
reorder, locked правила и replacement имеют разные намерения.

Для выбранной папки сначала строить read-only план по согласованному режиму:
replacement сохраняет целевой id/позицию, merge сохраняет текущие поля и записи,
copy создаёт новые id и уникальное имя с префиксом. Имена и адреса служат явному
обнаружению конфликтов, не заменяют идентичность элементов всей истории.
При диалоге с несколькими конфликтами собрать решения, затем заново сверить
ревизию и применить весь план одной операцией. Нельзя последовательно менять
папки до завершения пользовательского выбора и сохранения общего Before restore.

## Защита restore / Undo

IDB + chrome.storage.local не образуют общей транзакции. Обязательные стадии:

1. Сверить ревизию, построить полный target и план, проверить local quota.
2. В IDB сохранить operation id, подтверждённый before, target и protected rollback.
   Учесть оба состояния в history budget до изменения коллекций.
3. Согласованно записать коллекции и служебный маркер commit/revision.
4. Зафиксировать history result; после подтверждения показать успех и Undo.

После worker interruption сверить маркер и коллекции с before/target.
Если обнаружены сторонние изменения, не продолжать replacement автоматически.
Сохранить доступные версии и предложить понятный путь возврата.
Final IDB failure после local commit не должен лишать пользователя before,
объявлять повторное восстановление либо давать ложное сообщение «ничего не изменено».

Protected rollback не истекает вместе с плашкой или session epoch. Бюджет должен
сначала доказуемо вместить гарантию возврата; если это невозможно, restore не начинает
мутацию. GC не удаляет последнюю гарантированную точку.

## Связанные действия Undo

В dashboard есть краткие in-memory Undo snapshots, а popup использует
`quickSaveUndo`. После полного replacement старый Undo может ссылаться на
восстановленные id и отменить другую версию данных.

Проверить/инвалидировать ранее доступные краткие действия при замене коллекций
либо проверять generation/revision их исходного результата. Простого совпадения
id/URL недостаточно для принадлежности к прежней операции. При этом новый
долговечный Undo restore остаётся доступен. Добавить проверку двух открытых dashboard.

## Архив после восстановления

`expiredArchiveRecordIds` (`archive-retention.js:16`) считает возраст по
`completedAt`; `app.js:5746` запускает очистку при каждом старте dashboard.
Восстановленный архив со старыми датами может быть удалён сразу при перезапуске.

Исторические даты не подменять сегодняшними ради обхода очистки. Нужна явная
защита восстановленных записей от немедленного автоматического удаления, согласованная
с retention и пользовательской явной очисткой. Её метаданные должны переживать
worker/browser restart и учитывать несколько dashboard. В новом restorer реализована
отдельная карта id/completedAt/until с 30-дневной grace; до подтверждения нужно
показывать этот срок. Реальная dashboard очистка ещё не подключена к карте.

## Проверки для будущей реализации

- Одновременные popup save + dashboard move сохраняют обе подтверждённые правки.
- Restore против stale rename/drop/import не затирает новое состояние молча.
- Folder removal и create-folder+save дают один согласованный слепок.
- Browser-only события и workspace-only commit не создают слепков.
- Старый quick-save/dashboard Undo не меняет replacement поколение данных.
- Undo restore работает после browser restart; повтор request/Undo не удваивает запись.
- IDB before failure → ни одной local mutation; local failure → before сохранён;
  final IDB failure → возврат доступен и результат не выдаётся за неизменённый Atlas.
- GC удерживает before при истории около бюджета, включая большие коллекции.
- Архив старше retention после restore и restart не исчезает автоматически сразу.

Модульные гонки проверяются с управляемыми gates; дополнительно нужны native IDB,
worker interruption и несколько контекстов установленного расширения. Здесь тесты
не запускались на момент первичного аудита; новые unit/native протокольные проверки
и оставшиеся ограничения описаны в [progress](atlas-history-progress.md).
